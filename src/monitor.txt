sentinel_monitor — watch a background command and get its output as it happens

Starts a shell command in the background and sends each new stdout line to this session as a message, so you can react to an event without polling or a sleep loop. You can keep working; an idle session wakes up when a line arrives.

## When to use it
- Waiting for something to show up in ongoing output: a log line (`tail -f`), a CI or PR status change, a dev server crash, a training metric
- Watching any long-running command whose output you need line by line

## When not to use it
- A command whose only result is finishing (a build, a test run): run it as a background shell job and wait for its completion notice
- Interactive commands that need input

## Pipes: use line buffering
When piping through `grep`, always pass `--line-buffered`; otherwise grep buffers its output and lines arrive late or not at all.

  Right: tail -f /var/log/app.log | grep --line-buffered ERROR
  Wrong: tail -f /var/log/app.log | grep ERROR

## filter and until
Both take a JavaScript regular expression and are optional.
- `filter`: only matching lines are sent; the rest are dropped (they still appear in /monitors)
- `until`: the first line that matches is sent and the monitor stops. Use it for one-shot waits such as "tell me when CI finishes"
With both, `until` is checked only on lines that passed `filter`.

Examples:
- Only errors: filter="ERROR"
- Wait for CI: command="gh run watch <id>", until="(completed|failed)"
- Build errors until the build ends: filter="(error|fatal)", until="BUILD (SUCCESS|FAILED)"

An invalid regex returns an error and nothing starts.

## What arrives and when
- Lines are grouped: everything printed within 200 ms comes as one message, each line prefixed with [monitor:<id>]
- A non-zero exit is reported. A clean exit (code 0) is not, so use `until` when you need to know the moment something finishes
- stderr is not sent; it is kept in /tmp/sentinel-<id>-stderr.log and shown in /monitors

## Limits (the monitor stops and tells you)
- More than 100 lines per second: narrow the command or the filter
- A filter/until pattern that takes over 250 ms on one line: use a simpler pattern
- Lines longer than 64K characters are cut and marked

## Related
- sentinel_stop: stop a monitor by ID once you no longer need it
- sentinel_list: list running monitors
- The user can see every monitor, read its output and kill it with the /monitors command
